================================================================================
1. WHAT IS INKENGINE SUPPOSED TO DO? (THE PROBLEM IT SOLVES)
================================================================================

Inkling-2-Mini is a 26.4B-parameter Mixture-of-Experts (MoE) model with a
1-million-token context window. Even quantized to ~3-bit (UD-IQ3_XXS), the
model file is 10.86 GiB — which CANNOT fit inside an 8 GB VRAM GPU, let alone
with 64K–512K tokens of KV cache.

When you run Inkling-2-Mini on standard engines like llama.cpp / Unsloth Studio
on an 8 GB GPU + 16 GB RAM:
  - Static layer offloading treats all layers equally and spills weights across
    CPU/PCIe inefficiently.
  - Default compute/scratch buffers waste ~3.48 GiB of precious VRAM.
  - Result: ~10.6 tok/s decode and Out-Of-Memory (OOM) past ~32K–48K context.

InkEngine was built from scratch in standalone C++17 / CUDA / AVX2 — with ZERO
llama.cpp or ggml dependencies — to solve three goals:
  1. 100% custom serving engine tailored specifically to Inkling-2's unique
     Looped-MoE architecture.
  2. 3x+ faster generation and 2x+ faster prompt processing on consumer 8 GB
     GPUs without sacrificing output quality.
  3. Massive context windows (128K, 256K, 512K, up to 1M tokens) by seamlessly
     tiering BOTH model weights AND KV cache across VRAM -> RAM -> NVMe SSD.


================================================================================
2. WHAT IT ACTUALLY DOES UNDER THE HOOD (HOW IT WORKS)
================================================================================

InkEngine exploits two unique structural facts about Inkling-2-Mini:

  A) 3x Looped-MoE Architecture:
     - Inkling-2 has 24 physical layers, expanded into 48 logical layers per
       token:
         * Layers 0..5   (Prelude) : executed 1x per token (Outer)
         * Layers 6..17  (Core)    : executed 3x per token = 36 logical passes!
         * Layers 18..23 (Coda)    : executed 1x per token (Outer)
     - Every layer has 128 MoE experts, and only 8 experts activate per token.
     - Because the 12 Core layers account for 75% of all MoE work (36 of 48
       passes), keeping hot Core experts in VRAM (guided by a learned neural
       expert predictor) yields a 93–94% VRAM hit rate using less than half the
       model's size in VRAM!

  B) Hybrid Sliding-Window + Global Attention:
     - 40 of the 48 logical layers are Sliding-Window Attention (SWA = 1,024
       tokens, backed by a wrap-safe 1,152-slot ring buffer in v3.3). Their KV
       cache NEVER grows beyond 50.6 MiB total in VRAM — even at 1,000,000
       tokens!
     - Only 8 logical layers are Global Attention. InkEngine pages those 8
       layers in 64-token blocks across VRAM -> RAM -> NVMe SSD (with disjoint
       per-layer page tables), using INT8 Quest summaries + GPU Radix-Select
       Top-K to fetch only the most relevant historical pages on ultra-long
       contexts (256K–1M).

Exact 3-Tier Memory Split at 128K Context (RTX 4060 8 GB + 16 GB RAM, Q4_0 KV):
  - GPU VRAM (~7,590 / 8,188 MiB used, ~250–370 MiB Windows safety headroom):
      * Dense weights (attention, loop controllers, routers, LM head): 988 MiB
      * KV Cache (40 SWA = 50.6 MiB + 8 Global = 640.0 MiB + Quest = 32.6 MiB): 723.2 MiB
      * Dynamic Expert VRAM Pool (1,493 / 3,072 experts = 48.6%): 4,838 MiB
      * CUDA context, 97 Graphs, batch/PCIe staging buffers: ~1,042 MiB
  - System RAM (~5.6–6.2 GiB total process working set):
      * Tier-1 Expert RAM Pool (all 1,579 remaining cold experts): 5,367 MiB
      * Tier-1 Global KV RAM Pool: 512 MiB (up to 1,024 MiB cap)
      * Live prefix & turn-rewind snapshots: ~250–400 MiB
  - SSD Storage:
      * Model GGUF (read-only on SATA S:): 10.86 GiB (0 steady-state reads @ 128K!)
      * Persistent NVMe OpenCode KV Prefix Cache (%LOCALAPPDATA%\InkEngine\kv_cache): ~369–383 MiB (v3)
      * NVMe KV Page Swap (%TEMP%\inkengine_kv_swap.bin): 0 MiB @ 128K;
        grows automatically past 128K (~3.05 GiB @ 512K).

Everyday Serving Integration:
  - Runs as a hardened headless OpenAI-compatible HTTP server on
    http://127.0.0.1:8787/v1 (CSPRNG Bearer auth, Host allowlist, no wildcard
    CORS, 10s/30s socket timeouts, zero browser/GUI overhead).
  - Global `inkcode` command auto-manages the per-user API token in
    %LOCALAPPDATA%\InkEngine\api_token (syncing only inkengine in opencode.jsonc),
    auto-starts InkEngine in the background, and launches OpenCode CLI with full
    multimodal vision, tool calling, reasoning streaming, and KV prefix caching.

VERSION 3.1: Quality, Anti-Looping, Streaming Stability & Instant Retry Rewind
--------------------------------------------------------------------------------
Discovered and fixed during extended multi-turn OpenCode agent sessions after
the v3.0 GitHub release:

  1. Fixed Q4_0 KV Cache +0.5*d Systematic Rounding Bias (MAJOR QUALITY FIX):
     - `quant_block32_q4_0` in src/cuda_kernels.cu previously used
       `__float2int_rn(v * id + 8.5f)`. Adding +8.5f is only for truncating
       (int) casts; pairing it with round-to-nearest shifted EVERY K/V value
       by +0.5*d across all 48 layers and doubled worst-case Q4_0 KV error,
       triggering code corruption and repetition loops under `effort=max`.
     - Fixed to `__float2int_rn(v * id + 8.0f)` (exact unbiased rounding,
       cutting max Q4_0 KV error in half) and bumped NVMe checkpoint format
       from v1 -> v2 so stale biased checkpoints auto-rebuild cleanly.
  2. Fixed Speculative Rejection Greedy-Argmax Trap:
     - In `sample_from_logits` (src/model.cpp), rejected N-gram drafts with
       `d_idx < 0` previously fell back to `cand[0]` (pure greedy argmax),
       trapping repeating phrases in a greedy loop whenever N-gram fired.
     - Fixed to fall through to exact unbiased Leviathan residual sampling +
       fast unsorted double-precision sampling when top_k=0 & top_p=1.0.
  3. Official Inkling-2-Mini Sampling Defaults:
     - Changed HTTP server defaults from (T=0.6, top_p=0.95, top_k=40,
       min_p=0.05) to Thinking Machines / Unsloth's official recommended
       (T=1.0, top_p=1.0, top_k=0, min_p=0.0) with a time-mixed seed and
       live sampling telemetry in logs\server.log.
  4. Real OpenAI SSE `data:` Heartbeats During Large File Writes & Prefills:
     - Previously, buffering large tool calls (`write` / `edit` in ST_TOOL_JSON)
       sent zero TCP bytes for minutes, causing OpenCode `SSE read timed out`.
     - Now emits valid OpenAI empty-delta SSE events (`"delta":{}`) on every
       prefill batch (~1.5s) and every 16 tokens (~0.7s) while buffering tool
       JSON/headers + accurate `"length"` finish_reason when hitting max_tokens.
  5. Instant <1s TCP Disconnect Detection (`is_client_alive`):
     - Non-blocking <1 us Winsock `select + MSG_PEEK` check detects TCP FIN/RST
       immediately during both prefill and decode.
     - Eliminates zombie requests that previously blocked the server for 5–12+
       minutes and caused `ProviderHeaderTimeoutError: 300000ms` on retries.
  6. Lightweight ~49 MiB Zero-Global-Copy In-Place Turn-Rewind KV Snapshot:
     - Saves only ShortConv + SWA state (~49 MiB, ~4 ms) at the prompt's 64-
       token page boundary (and every 4,096 tokens during huge prefills).
     - On retries/cancels after partial generation (even at 36K–512K context),
       rewinds in-place in ~4 ms while keeping all Global KV pages intact —
       turning 5-minute retry re-prefills into ~1-second resumes!
  7. OpenCode Timeout Configuration:
     - Disabled OpenCode's default 5-minute (300,000 ms) local limits in
       opencode.jsonc (`timeout`, `headerTimeout`, `chunkTimeout`: `false`).

VERSION 3.2: Native Zero-Overhead Multimodal Vision (GPU-Streamed `inkling2v`)
--------------------------------------------------------------------------------
Added full multimodal vision so Inkling-2-Mini can directly see screenshots,
Three.js 3D renders, UI layouts, diagrams, and photos inside OpenCode and the
OpenAI HTTP API — WITHOUT touching text decode speed or stealing VRAM/RAM from
MoE experts!

Architecture Decision (Why GPU-Streamed On-Demand Won Over Permanent CPU RAM):
  - Pinning the 610 MB `mmproj-F16.gguf` in VRAM would evict ~185 hot MoE
    expert slots and slow down every text token.
  - Pinning it in CPU RAM (AVX2) would steal 610 MiB from 16 GB RAM (pushing
    cold MoE experts to SSD) AND take ~5–15 seconds per image on CPU.
  - Instead, InkEngine v3.2 streams `mmproj-F16.gguf` layer-by-layer in tiny
    8–9 MiB slices through the engine's ALREADY-ALLOCATED 14 MiB PCIe prefill
    staging ring directly onto RTX 4060 WMMA Tensor Cores, reuses the idle
    Q/K/V activation slab for single-pass FFN, and calls `cudaFree` on all
    temporary activation buffers the instant each image finishes!
  - Result: 0 MiB permanent VRAM, 0 MiB permanent RAM (<100 KB GGUF header
    only), identical 1,494 VRAM expert slots, and 0.0% text-only slowdown!

What was added on top of v3.1:
  1. 6 Custom Vision CUDA Kernels (src/cuda_kernels.cu/.cuh):

  2. Standalone `VisionEncoder` (src/vision.cpp/.h):

  3. Seamless Multimodal KV Prefix Caching & `tok_norm_` Bypass (src/model.cpp):

5. WHEN INKENGINE IS BENEFICIAL VS. WHEN IT IS NOT
================================================================================

  [HUGE WIN] 6 GB - 12 GB VRAM GPUs (RTX 3060/3070/3080/4060/4070 & laptops):
    - Primary target hardware. 2.5x–3.5x faster than llama.cpp, 2.2x faster
      prefill, zero OOM from 64K up to 512K+ context.

  [GOOD WIN] 16 GB VRAM GPUs (RTX 4060 Ti 16G / 4070 Ti Super / 4080 / 5080):
    - Worth using for higher-bit quants that exceed 16 GB, ultra-long 256K–1M
      context via NVMe KV paging, 97 captured CUDA Graphs, zero-VRAM coding
      speculative decoding, and <0.2s persistent NVMe OpenCode prefix caching.

  [USUALLY NOT NEEDED] 24 GB - 32 GB+ VRAM GPUs (RTX 3090 / 4090 / 5090):
    - If your quant + context fits 100% in VRAM, llama.cpp / ik_llama.cpp with
      -ngl 99 is simpler and has mature full-GPU prefill kernels (unless you
      specifically want 512K–1M SSD KV, speculative coding boost, or persistent
      disk KV prefix caching).

  [NOT SUPPORTED YET]:
    - Multi-user concurrent serving (single-user engine; use vLLM / SGLang).
    - Non-Inkling-2 models (exclusively general.architecture = inkling2).
    - Linux / macOS / AMD / Apple Silicon (currently Windows x64 + NVIDIA
      sm_75+ + AVX2 CPU).
    - Moving to 4-bit UD-Q4_K_M (~16.6 GB) on 8 GB VRAM + 16 GB RAM: would
      require adding Q4_K/Q5_K/Q6_K CPU AVX2 dot-product kernels and would
      spill ~3.5–4.5 GiB of experts onto SSD (estimated ~16–22 tok/s on NVMe
      or ~11–17 tok/s on SATA vs 27–33 tok/s today on UD-IQ3_XXS).
